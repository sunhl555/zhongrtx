# OTA智能调价助手 — 设计方案

**日期**: 2026-06-09
**状态**: 设计完成，待用户审核
**作者**: 中瑞天禧酒店

---

## 1. 项目目标

为酒店提供一套OTA智能调价决策工具，解决当前手动搜价+人工调价的痛点。核心价值：
- 自动抓取竞对价格和自家库存，无需手动打开携程/别样红
- 基于算法自动生成调价建议
- 防止客人因价格变动产生冲突
- 先自己酒店用，验证效果后可产品化销售

---

## 2. 核心功能

### 2.1 竞争圈管理
- 手动添加/删除竞对酒店（输入携程酒店名或链接）
- 后续预留携程EBK数据同步接口
- 支持手动录入竞对价格（爬虫失败时的备用方案）

### 2.2 房型与成本管理
- 设置自家房型：名称、成本底价（用户自定义）、总间数
- 房型映射：别样红PMS房型名 ↔ 携程OTA房型名
- 淡季/旺季模式切换
- 旺季目标利润率输入

### 2.3 自动数据抓取
- **别样红PMS**：模拟登录抓取实时库存（各房型剩余间数、已售间数）
- **携程前台**：搜索竞对酒店，抓取各房型挂牌价
- 手动/定时触发（默认每日早9点自动执行）

### 2.4 智能调价引擎

**淡季模式（智能跟随）**：
- 目标：以满房为优先，动态调整价格抢客
- 逻辑：
  - 库存 > 40%：建议价 = max(竞对最低价 - 5元, 成本 + 10元) —— 激进抢客
  - 20% ≤ 库存 ≤ 40%：建议价 = max((竞对最低价 + 竞对均价)/2, 成本 + 30元) —— 平衡跟随
  - 库存 < 20%：建议价 = max(竞对均价 + 10%, 成本 + 50元) —— 涨价保利润
- 所有阈值和幅度用户可调

**旺季模式（利润导向）**：
- 用户输入目标利润率（如30%）
- 系统分析竞对价格区间，判断目标利润是否可达成
- 给出建议价（满足利润 + 市场可接受范围内）

### 2.5 客人防冲突机制
- **规则1 — 已订不改价**：按订单锁定价格，客人预订后价格永久不变
- **规则2 — 价格只往上走**：临近入住日期价格只涨不跌（早订优惠，晚订贵）
- **规则3 — 每日一调**：每天只在固定时间统一调价一次，避免频繁波动

### 2.6 调价建议与执行
- 仪表盘展示调价建议（建议价、原价、理由）
- 用户审核确认后，手动去携程EBK改价
- 记录每次调价历史，可追溯

### 2.7 数据报表
- 价格走势图（本店 vs 竞对）
- 入住率趋势
- 利润分析
- 导出Excel

## 3. 技术架构

### 3.1 技术选型

| 层 | 技术 | 说明 |
|---|---|---|
| 前端 | Vue.js 3 + Element Plus | 浏览器访问，响应式布局 |
| 后端 | Python FastAPI | REST API + 爬虫 + 算法 |
| 数据库 | SQLite | 本地单文件，零配置 |
| 爬虫 | Playwright | 模拟浏览器，处理JS渲染页面 |
| 定时任务 | APScheduler | Python轻量级定时调度 |

### 3.2 部署架构

```
[浏览器] ←→ [FastAPI :8888] ←→ [SQLite]
                  ↓
           [Playwright 爬虫]
           /              \
    [别样红 PMS]      [携程前台]
    (自家库存)        (竞对价格)
```

- 本地运行：在你的Windows电脑上启动服务，浏览器访问 `localhost:8888`
- 局域网访问：同一WiFi下手机/平板可访问
- 后期扩展：可部署到云服务器，加账号系统变成SaaS

## 5. 爬虫设计

### 5.1 别样红PMS爬虫
- **目标URL**: `https://zrtx.beyondh.com:8101/`
- **方式**: Playwright 模拟登录 → 进入仪表盘 → 提取房型库存数据
- **频率**: 每日1-2次（调价前执行）
- **输出**: 各房型剩余间数、已售间数
- **凭证**: 用户提供账号密码，加密存储于本地配置

### 5.2 携程竞对价格爬虫
- **目标**: 携程酒店搜索页面
- **方式**: Playwright 模拟搜索 → 进入竞对酒店详情 → 提取房型价格
- **频率**: 每日1-2次（调价前执行）
- **输出**: 各竞对各房型当日价格
- **反爬策略**: 使用真实浏览器指纹、随机延迟、请求间隔

### 5.3 爬虫失败处理
- 自动重试3次
- 失败后使用最近一次成功抓取的数据
- 仪表盘标注"数据可能不是最新"
- 支持手动触发重新抓取

## 7. 非功能需求

### 7.1 数据安全
- 所有数据存储在本地SQLite，不上传云端
- 别样红/携程账号密码加密存储
- 数据库文件放在用户目录下，定期建议备份

### 7.2 性能
- 爬虫执行时间 < 2分钟（5个竞对以内）
- 页面响应 < 1秒
- 数据保留至少1年

### 7.3 可用性
- 电脑开机自启动服务（Windows计划任务或启动文件夹）
- 服务崩溃自动重启
- 操作日志记录便于排查

### 7.4 扩展预留
- 数据库设计预留 hotel_id 字段（多酒店扩展）
- API设计遵循RESTful，便于后期小程序对接
- 调价规则设计为可插拔（便于添加新策略）

## 附录：关键设计决策记录

1. **为什么选择SQLite而非MySQL？** — 本地部署，零配置，单文件备份方便。后期上云可迁移到PostgreSQL。
2. **为什么纯建议而非自动改价？** — 携程EBK改价需API权限，且自动改价风险高。用户审核后再执行更稳妥。
3. **为什么爬虫用Playwright而非requests？** — 携程页面大量JavaScript渲染，需要真实浏览器环境。
4. **为什么价格只涨不跌？** — 防止已预订客人发现降价后要求退差价，同时"早订优惠"符合用户心理预期。
